This isn't background reading — it's a setup checklist. Work through it section by section before the hackathon day. The optional items are genuinely optional, but candidates who arrive with them done tend to use the time well. Nothing here needs to be submitted — just show up ready.
01 Your machine
Hardware meets the minimum required
The session involves running a Spring Boot backend, a React or Angular dev server, and making live LLM API calls concurrently. That's more load than it sounds on a slower machine. Check yours before the day.
✓ 8 GB RAM minimum ✓ 4-core CPU ✓ 10 GB free disk ⚠ 4 GB RAM — likely too tight
Stable internet, backup ready required
You'll be making live LLM API calls throughout the session. If your home connection is unreliable, set up a mobile hotspot as backup before the day — not during it. Download all Maven and npm dependencies in advance so your builds run from cache on session day.
Screen recording tested required
You'll submit a 5-minute demo video. Test your recording setup now — not in the last 20 minutes of the session. Record a 30-second test clip and confirm the output is watchable before the day.

Good options: Loom (simplest, free tier is enough), OBS Studio, macOS QuickTime, Windows Game Bar (Win + G).
02 Java & backend stack
Java 17+ installed and on PATH required
Run java -version — output should show 17 or higher. Recommended: Eclipse Temurin 21 LTS. Avoid Java 8 or 11 — Spring Boot 3.x won't run on them.
Maven or Gradle installed required
Run mvn -version or gradle -version. Pick one and stick with it for the session. Maven 3.9+ or Gradle 8+ recommended. If you plan to use the IDE wrapper (./mvnw), confirm it resolves without needing network access.
Spring Boot 3.x starter project running required
Don't start from a blank project on session day. Go to start.spring.io now and generate a project with: Spring Web, Spring Data JPA, Spring Validation, Spring Actuator, and H2 Database. Run it locally and confirm http://localhost:8080/actuator/health returns {"status":"UP"}. Save this as your session starter.
IDE configured with Spring Boot support required
IntelliJ IDEA (Community or Ultimate), VS Code with the Java Extension Pack, or Eclipse. Whichever you use — confirm run/debug works for a Spring Boot app without using a terminal. If you use Lombok, enable annotation processing now.
REST client ready for endpoint testing required
Postman, Insomnia, Bruno, or IntelliJ's built-in .http file support — whichever you're fastest with. You'll need to smoke-test your four endpoints quickly before moving on to the next task. Have this ready before the session starts.
03 Database
H2 in-memory database working required baseline
H2 is included in your Spring Boot starter and needs no installation. Confirm the console is accessible at http://localhost:8080/h2-console. Add these to your application.properties now:
Recommended config
spring.h2.console.enabled=true
spring.datasource.url=jdbc:h2:mem:hackathon
spring.jpa.show-sql=true
spring.jpa.hibernate.ddl-auto=create-drop
PostgreSQL available locally or via Docker preferred
Postgres is the preferred database for the session. If you have Docker, this is a single command:

docker run --name hackathon-db -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=hackathon -p 5432:5432 -d postgres:16

Without Docker: install PostgreSQL 15 or 16 and create a hackathon database. Confirm your Spring Boot starter connects to it before the session.
04 Frontend stack
Node.js 20+ and npm installed required
Run node -v and npm -v. Node 20 LTS is recommended. If you use nvm, run nvm install 20 && nvm use 20. Both React (Vite) and Angular CLI require Node 18 at minimum — Node 16 won't work.
Decide your framework before the day required
The brief accepts React 18 or Angular 17. Your choice is documented in the ADR, so commit to it now. Switching frameworks mid-session is an expensive mistake. If you haven't touched one of them recently, spend an hour on a small practice project this week — the muscle memory matters on the day.

React 18 — scaffold it now:
npm create vite@latest hackathon-ui -- --template react
cd hackathon-ui && npm install && npm run dev
Confirm http://localhost:5173 shows the Vite welcome page.

Angular 17 — scaffold it now:
npm install -g @angular/cli@17
ng new hackathon-ui --routing=false --style=css --standalone
cd hackathon-ui && ng serve
Confirm http://localhost:4200 shows the Angular welcome page.
Angular 17 note
Angular 17 introduced the standalone component API, which is meaningfully different from the NgModule-based approach in older versions. If you last used Angular 14 or earlier, spend some time with the Angular 17 standalone docs before the session — it'll save you friction on the day.

Test before the day
Send a basic prompt to your chosen provider and confirm you get a response back. Rate limit errors and authentication failures on session day are avoidable. Store your key as an environment variable — never commit it to your repo.
Understand structured JSON output from LLMs worth reading
The session requires the LLM to return a specific JSON schema: {"agentId":"...","confidence":0.85,"reasoning":"..."}. LLMs don't always comply without explicit instruction. Understand how to prompt for reliable JSON output and how to parse and validate the response defensively in Java. Gemini and Groq both support a JSON response mode — know how to enable it for your chosen provider.

Also worth understanding: how to detect and handle a hallucinated agentId that doesn't exist in your database. This is a specific failure mode you'll need to address in the session.
06 Developer tooling
Git configured, GitHub access confirmed required
Run git config --list and confirm user.name and user.email are set. Create a test private repo on GitHub now and push a commit to confirm your SSH key or personal access token works without a browser prompt. You'll make the repo public at submission time.
AI coding assistant set up and familiar required
AI coding tools are expected — not optional. Set up at least one before the session: Cursor, GitHub Copilot, or Claude in your browser. More importantly, be comfortable using it. On session day you won't have time to learn a new tool. Know how to use it to generate boilerplate quickly, and know how to read what it produces critically — that's the combination that works.
Docker installed and running optional but useful
Useful if you plan to run Postgres via Docker or containerise your app. Run docker run hello-world to confirm it's working. On lower-end machines, Docker adds memory overhead — only use it if you're comfortable with the tradeoff.
07 Deployment — optional, above and beyond
This section is entirely optional
A working local demo is all that's required. Deploying to a live URL demonstrates end-to-end ownership and is a nice touch — but only attempt it if your core tasks are solid and your ADR is complete. Don't trade backend quality for a live URL.
Dockerfile for Spring Boot backend bonus
Prepare and test a multi-stage Dockerfile now — not on session day. Build the jar in a Maven image, run it in a slim JRE image. Confirm docker build and docker run both work locally. A docker-compose.yml that wires backend + Postgres together is a clean addition.

Starter pattern:
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /app
COPY . . && RUN mvn package -DskipTests
FROM eclipse-temurin:21-jre
COPY --from=build /app/target/*.jar app.jar
ENTRYPOINT ["java","-jar","/app.jar"]
Frontend deployed to Vercel or Netlify bonus
Connect your GitHub repo to Vercel (React) or Netlify now so deployment on session day is a single git push. Configure your backend API base URL as an environment variable — not hardcoded in the source.
Backend deployed to Railway, Render, or Fly.io bonus
Railway is the simplest option for Spring Boot — it detects Maven/Gradle projects and can provision a Postgres database automatically. Render and Fly.io both support Docker-based deploys. Connect your repo now so deployment is push-to-deploy on the day. Note: free tier cold starts can be slow — keep that in mind when recording your demo.

09 Things that trip people up

These aren't hypothetical — they're the most common avoidable mistakes. Worth a read.

Leaving dependency downloads for session day
Run a full Maven build and npm install now so everything is cached locally. On session day your builds should be instantaneous. Waiting on a slow registry at hour two is demoralising and avoidable.
Writing the ADR at the end
The ADR should be a living document throughout the session — write each entry right after making the corresponding decision. Reconstructing reasoning four hours later when you're tired produces weaker entries. The walkthrough will reflect it.
Committing your API key to the repo
Store your key as an environment variable: LLM_API_KEY. Read it in Spring Boot via @Value("${llm.api-key}") and set it in application.properties as llm.api.key=${LLM_API_KEY}. Add any local properties file to .gitignore. A public GitHub repo with an exposed key will have it revoked within minutes of pushing.
Treating the LLM as infallible
The LLM will occasionally return malformed JSON, suggest an agent that doesn't exist in your database, or time out entirely. These aren't edge cases — they're expected failure modes you need to handle explicitly. Build your fallback logic before you test the happy path, not after.
Auto-assigning in the agentic loop
The agentic loop queues suggestions — it does not auto-assign. The system reasons and acts, then hands the decision to ops. Building an auto-assign loop isn't "more complete," it's a misunderstanding of the design requirement. If you're unsure about the distinction, read the Agentic Layer section of the brief carefully before building T-4.
Spending too long on the UI at the expense of the backend
This is primarily a backend and systems design screen. The UI's job is to show the system working — especially the re-plan badge appearing after an agent goes offline. A clean, functional interface that proves the agentic loop works scores better than a polished UI built on a weak backend. Prioritise accordingly.
